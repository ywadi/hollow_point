## Why

`docs/api` is generated by `zig build docs`, and today that step is **both**
manual and uncached — the worst pair.

- `build.zig:422-425` makes it deliberately on-demand: *"making `zig build` fail
  for someone who only wants to compile the engine would be a poor trade for
  output that changes rarely."* The reasoning is sound; the consequence is that
  nobody runs it.
- `build.zig:455` sets `docs.has_side_effects = true`, so when it *is* run it
  always does full work, regardless of whether a public header changed.

So the loop is: change a public header → forget → push → the `api-docs-current`
job fails → run `zig build docs` by hand → commit → push again. That is a CI job
catching a mistake the build should have made impossible, which is the exact
inversion `build.zig:416-420` says it wants to avoid:

> A build step rather than only a CI check, because stale output here is a
> *correctness* bug [...] Generating it as part of the build means it cannot
> drift; the CI gate is then trivially "run this, then fail if the tree is
> dirty".

The intent was right and the wiring does not deliver it. **Observed on T0100**:
adding `onFixedUpdate`/`onLateUpdate` turned a green run red on the docs job
alone, and cost an extra commit and CI cycle (`c9116a8` → `6ceb488`).

## Done when

- [x] Changing a public header regenerates `docs/api` as part of the ordinary
      build, with no separate command to remember
- [x] Changing anything that is *not* a public header does not re-run the
      generator at all — verified by observing it skip, not assumed
- [x] A developer without python or libclang still gets a working `zig build`,
      with a warning rather than a failure
- [x] `api-docs-current` still fails on drift, so the backstop is intact for the
      case where someone bypasses the build

## Notes / findings

**Do not start before T0122.** This is a `build.zig` change and there is
currently no way to verify one locally on the WSL side; iterating on the build
system through CI is slow and error-prone in exactly the way that produces a
second wrong commit.

**123.4 is the part that can go quietly wrong.** Everything else is mechanical.
The baseline exists so new public API must be documented from its first commit
while the existing 117-defect gap is paid down; a change that makes the
generator run automatically must not also make `--write-baseline` easier to
trigger by accident.

## Evidence

### What actually made it uncacheable

`has_side_effects = true` was the visible half. The half that would have wasted
an afternoon: `docs.stdio = .inherit` **also** forces side effects, in
`Step/Run.zig`:

```zig
fn hasSideEffects(run: Run) bool {
    if (run.has_side_effects) return true;
    return switch (run.stdio) {
        .infer_from_args => !run.hasAnyOutputArgs(),
        .inherit => true,
        ...
```

So dropping `has_side_effects` alone changes nothing. The step needs a declared
output as well, and zig cannot model output written into the source tree — hence
`--stamp`, a cache-side file that exists purely so the Run has an output to
declare. Checked before relying on it that stderr is still piped and replayed on
failure (`.infer_from_args` → `.pipe` for stderr, line 1565), which is where the
generator writes every defect; only the "check passed" summary is dropped.

### The cache does what it claims — observed, not assumed

```
non-header change (.cpp):        generate api docs cached
unrelated doc file:              generate api docs cached
public header content change:    generate api docs success 5s
  (settle)                       generate api docs cached
DELETE docs/api entirely:        generate api docs success 5s
  files restored: 12
delete ONE generated file:       generate api docs success 5s
  files restored: 12
```

The positive control matters as much as the negative one: `cached` on its own is
equally consistent with "never runs", so the header-change row is what makes the
other rows mean anything.

### The generated output had to become an input

First attempt tracked only headers, the generator and the baseline. That is
subtly wrong, and it was **measured rather than reasoned about** — the first
version of this wiring produced:

```
DELETE docs/api entirely:        generate api docs cached
=== docs/api restored and clean? ===
ls: cannot access 'docs/api': No such file or directory
```

`rm -rf docs/api && zig build docs` scored a cache hit and restored nothing,
because with the directory gone the input set collapses back to exactly the set
the first run hashed. Fixed by declaring the generated markdown as an input too,
and by forcing a run when the directory is absent or empty — an empty input set
must mean "regenerate", never "nothing to do".

The cost is convergence rather than instant settling: regenerating changes the
step's own inputs, so one further run happens and writes byte-identical output
before it caches. Verified it terminates rather than looping:

```
run 1: generate api docs success 5s
run 2: generate api docs success 5s
run 3: generate api docs cached
run 4: generate api docs cached
```

### Wired into the ordinary build

```
Build Summary: 3/3 steps succeeded
install success
+- build (linux-x86_64, Release) success 3m
+- generate api docs cached
```

Hung off the default step, `all`, and every per-target step — a developer whose
habit is `zig build linux` would otherwise never regenerate, which is the exact
failure being fixed. Deliberately **not** hung off `test`: the inner loop stays
about tests, and CI's test jobs (`zig build test`) are unchanged.

### Degradation is detection, not assumption

Both branches, in a stripped environment:

```
=== BRANCH 1: no python3 on PATH at all ===
warning: python3 with libclang bindings not found -- docs/api will not be regenerated by this build.
  Install them with `pip install libclang` so a public-header change cannot leave the API reference stale.
  The build continues; CI's api-docs-current job remains the backstop.
exit=0

=== BRANCH 2: python3 present, libclang import fails ===
warning: python3 with libclang bindings not found -- ...
```

The import is checked, not merely the interpreter: `python3` exists nearly
everywhere and `clang.cindex` is the part that is actually missing.

### 123.4 — the ratchet, which is where this could have gone quietly wrong

A new undocumented public symbol still fails, and now fails the *ordinary*
build:

```
error: 1 new API documentation defect(s).
  Public API must be documented as it is written. Add the missing
  comment or @param tag -- do not add it to the baseline.
Build Summary: 0/2 steps succeeded (1 failed)
```

The rewrite path stays deliberate and uncached — `has_side_effects` is set back
to true for `-Ddocs-baseline` specifically, since it writes the file the other
mode is judged against:

```
  rewrite run 1: generate api docs (rewriting baseline) success 5s
  rewrite run 2: generate api docs (rewriting baseline) success 5s
a3254b8b3b7b70f93f166469a2707edd  tools/api_docs_baseline.txt   (before)
a3254b8b3b7b70f93f166469a2707edd  tools/api_docs_baseline.txt   (after)
```

Never cached across two consecutive runs, and byte-identical at 117 defects
afterwards. The ratchet did not shrink by being run.

### CI

`api-docs-current` is untouched and still the backstop: it regenerates and fails
on a dirty tree, and its runner restores only `.harness`, not `.zig-cache`, so
the step has no cache to hit and genuinely re-runs. `full-build.yml` builds via
target steps, so it now reaches the docs step and will warn-and-skip if that
runner lacks libclang rather than failing.

## What is not verified

**No full `zig build` was run in the degraded environment.** Branch 1 and 2
prove detection fires and the graph still constructs (`exit=0`), not that a
complete C++ build succeeds without python. It cannot easily prove that here:
DiligentCore pip-installs jinja2 during configure, so a python-less configure
fails for reasons that have nothing to do with this wiring. The claim being made
is the narrow one — the docs step no longer participates, and nothing else
changed.

**CI has not yet run against this change.** Pushed at the same time as T0125;
the result belongs in this file before anyone trusts it.

## Notes / findings

**The `.inherit` interaction is the thing worth remembering.** The ticket framed
this as "drop `has_side_effects`", and doing only that would have produced a
change that looks right, passes review, and caches nothing. Reading
`Step/Run.zig` rather than trusting the field name is what caught it.

**Declaring the output as an input reads backwards and is load-bearing.** It is
the only way the cache can notice that the artefact it is responsible for was
deleted or edited, given that the real output lives in the source tree where zig
has no model for it.

**A self-inflicted lesson worth recording:** during verification,
`touch engine/include/hp/log.hpp` *created* an empty header rather than touching
an existing one, the generator documented it, and `docs/api/index.md` picked up
an entry for a file that never existed. Caught by checking `git status` rather
than by the build, which had no reason to object. Cleaned up and the tree
verified clean afterwards — but a scripted `touch` on a path that may not exist
is a footgun in a repo where generated output is checked in.
