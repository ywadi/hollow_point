# HollowPoint

A 3D game engine in C++20, built to power **several** games for a small studio —
so the engine is a reusable library and a game is a separate project, not
something that lives in this repository.

This file is the entry point. It does not repeat what the documents below say;
it tells you which one answers your question, and the few things that will bite
you in the first ten minutes.

## Working a ticket — this is mandatory

The backlog README states it, and it gets forgotten anyway:

1. **`git mv` the ticket into `inprogress/` before doing any work**, and set its
   `Status` line to match. **A ticket's state is the folder it sits in.** Setting
   the Status field while leaving the file in `open/` is the one inconsistency
   the whole scheme exists to prevent — and it has happened.
2. **Tick `- [ ]` → `- [x]` as you go**, not in one commit at the end. The board
   renders progress from these.
3. **Append findings to `## Notes / findings` as you discover them** —
   especially anything surprising, anything that turned out wrong, and anything
   you could not verify. This is what survives a context reset.
4. **Only move to `completed/` when verified, with the evidence pasted in.** A
   ticket that overstates what was achieved is worse than one left open. If a
   "Done when" was not met, say so plainly instead of ticking it.

Run `python3 tools/check_backlog.py` before you commit backlog changes. It
verifies the folder, the `Status` field and the board row agree, and that every
link resolves.

**If a ticket is blocked on something that will not exist for a long time**,
prefer closing it on what it achieved and moving the remainder to the ticket
that unblocks it, rather than leaving it open near the top of the queue. See
T0095 → T0105 and T0054/T0056 → T0025 for how that was done and why.

## Build

```sh
./bootstrap.sh                 # or .\bootstrap.ps1 -- installs the pinned toolchain
export PATH="$PWD/.harness/zig/linux-x86_64/0.16.0:$PATH"

zig build linux                # or windows / all
zig build test -Dtest=all      # both targets; wine runs the Windows suite
zig build docs                 # regenerate + CHECK the API reference
zig build dist                 # stage runnable output
```

Everything is pinned in `.harness/` — zig, cmake, ninja. Nothing on `PATH` is
required, and the build says so loudly if it falls back to something there.

**Run the editor:** `./build/linux-x86_64-release/apps/editor/hp_editor`

## Traps that will cost you an hour

- **Submodules.** `git pull` does not fetch them. If C++ suddenly fails to find
  `doctest/doctest.h` or `SDL3/SDL.h`, run
  `git submodule update --init --recursive`.
- **The Linux build is hermetic.** X11/GL resolve from `third_party/sysroot/`,
  not `/usr`. If a dependency's CMake auto-detects the *host* (SDL does this),
  it will link against libraries the sysroot does not carry and fail — or worse,
  succeed only on your machine. Every backend must be chosen explicitly.
- **Windows has no RPATH.** A `.exe` finds DLLs in its own directory and on
  `PATH`, nowhere else. A missing DLL is silent: the process produces no output
  at all.
- **`dist` must be tested with the build tree gone**, not merely moved. An
  absolute build-tree path baked into RUNPATH passes both "run it in place" and
  "copy the folder elsewhere" on the machine that built it.
- **Verify with the whole output, not a filtered tail.** Truncating a test
  summary has twice hidden a failing bucket here. When a check fails, suspect
  the check before the code — that has been right more often than not.

## Architecture in six lines

- `engine/` is a **shared** library. The editor, the runtime and every gameplay
  module link the same copy, so engine state exists once per process (**D12**).
- Gameplay is **C++ against the real headers in lockstep** — no C ABI, no
  scripting (**D12**, **D14**). A build id refuses a mismatched module (T0104).
- `apps/editor` and `apps/runtime` are **consumers** of the engine. The editor
  disappears on export, so anything the game needs at runtime lives in `engine/`.
- `samples/sandbox/` is the engine's own sample gameplay module. **It is not
  "the game"** — real games are separate projects (T0109).
- All content is addressed through a **virtual filesystem** (**D13**); packs,
  patches and DLC are one mechanism, not three.
- Particles are **GPU-only and purely cosmetic** — gameplay never reads their
  state (**D15**).
